# 运行时组合

更新：2026-10-14。范围是8767对象工作台，不包括只供研究脚本加载的隔离补丁。

## 入口与组合顺序

唯一日常入口是`tools/object_workbench.py`：进程启动时调用一次`build_backend()`，创建一个MuJoCo owner、一个Harness和一个HTTP服务。其他`tools/check_*.py`可以在各自独立进程内调用构造器；不要在已经启动的工作台进程中再次构建。

Harness继承链由当前模块声明为：

`TransitHintHarness → CompactHarness → PolicyRouteHarness → IntentHarness → ActHarness → StageHarness → BottleHarness → PoseHarness → TaskHarness → ObjectTransportHarness → ObjectRelayHarness → ObjectGPUHarness → ObjectHarness → SceneHarness → CandidateHarness → CompositeHarness → Harness`

模型HTTP请求按Harness实例组合：工具可见性（`VisibleRequests`）、当前阶段上下文（`StageRequests`）、工具结果压缩（`CompactRequests`）、provider协议检查（`CheckedRequests`），最后进入标准库`urllib`。实际请求链为`VisibleRequests → StageRequests → CompactRequests → CheckedRequests → urllib`。`Harness`保存自己的`request_transport`；这些适配器不再替换`harness.agent.urllib`模块别名。安装同一provider适配器是幂等的，另一个Harness仍持有自己的传输层。API响应和动作回执不会被视为同一层证据。

## 已知边界与P1.3处理顺序

- 多个安装器修改模块级类、函数或工具列表，调用顺序会影响后续安装器读取到的基类和schema；新服务进程会重新从固定入口组合，现有运行不支持原地卸载/重新安装。
- `build_backend()`现在在同一进程只允许调用一次；再次调用会明确要求使用新进程。每层安装错误会带层名，阻止静默地在部分修改过的进程里继续重试。
- `/api/status`和`/health`的内部`runtime_composition`字段报告本进程实际Harness/Service MRO、安装顺序、planner factory和当前HTTP request中间件栈。空闲且还没有API调用时只显示`CheckedRequests → urllib`；Harness的chat方法会按继承顺序懒装工具可见性、阶段与Compact适配器。本轮没有为检查这条链调用真实API。
- 日常入口的`harness.fast_grasp`路由已由fixture证明被更外层专用路由完整遮蔽：单臂放置走`task_placement`，空场景交接抓取走`free_transport`，有障碍时走`margin_grasp`。从日常安装顺序移除后这些路由结果保持一致；`harness.fast_grasp.install_isolated`仍供研究脚本显式调用，不再作为默认组合层。
- `stages.install_isolated(...)`、`intent.install_isolated(base)`、`policy_route.install_isolated(base)`、`compact.install_isolated(base)`和`transit_hint.install_isolated(base)`不改模块级状态，只返回以当前Harness为父类的新类型。`StageRequests`在当前Harness首次聊天时按实例挂载。现单独列为`harness_composition_order`；runtime fixture证明父类字典不变，平台报告`["harness.stages", "harness.intent", "harness.policy_route", "harness.compact", "harness.transit_hint"]`。
