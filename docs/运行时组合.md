# 运行时组合

更新：2026-10-14。范围是8767对象工作台，不包括只供研究脚本加载的隔离补丁。

## 入口与组合顺序

唯一日常入口是`tools/object_workbench.py`：进程启动时调用一次`build_backend()`，创建一个MuJoCo owner、一个Harness和一个HTTP服务。其他`tools/check_*.py`可以在各自独立进程内调用构造器；不要在已经启动的工作台进程中再次构建。

Harness继承链由当前模块声明为：

`TransitHintHarness → CompactHarness → PolicyRouteHarness → IntentHarness → ActHarness → StageHarness → BottleHarness → PoseHarness → TaskHarness → ObjectTransportHarness → ObjectRelayHarness → ObjectGPUHarness → ObjectHarness → SceneHarness → CandidateHarness → CompositeHarness → Harness`

工厂与进程级组合按`build_backend()`实际顺序：

| 次序 | 模块/入口 | 改动面 |
|---|---|---|
| 1 | `harness.composite.install_isolated` | 全局Harness、Workspace、计划校验器、工具定义；将RelocationPlanner替换为回执报告包装 |
| 2 | `sim.grasp.install_isolated` | `sim.service`中的TAMP与Relocation规划器类 |
| 3–10 | `harness.candidate`、`scene`、`objects`、`object_handover`、`object_transport`、`task_queue`、`poses`、`bottle` | 依次改写全局工具schema/catalogue/校验器，提供以上Harness继承链 |
| 11 | `harness.bottle.service_factory` | 返回工作台服务工厂；上游组合从poses/task_queue/objects继续委托 |
| 12–16 | `connected_placement`、`fast_grasp`、`margin_grasp`、`free_transport`、`task_placement` | 逐层替换`sim.service.TampPlanner`并包装服务工厂 |
| 17 | `sim.scene_library.service_factory` | 包装工厂以编译用户选中的附加物体场景 |
| 18–19 | `sim.scene_curobo.install_isolated`、`sim.cache_curobo.install_isolated` | 替换GPU规划器和全局GPU请求函数，绑定当前场景几何与worker版本 |
| 20 | 可选的`OPENARM_SCENE_OBJECTS`启动配置 | 将启动时选择传入`OpenArmEnv`；页面仍通过owner线程及新观测切换场景 |
| 21 | `harness.policy_trace.install_isolated` | 替换`sim.service.make_client`和`PolicyTiming`，只记录本地VLA预测证据 |
| 22–27 | `stages`、`act_adapter`、`intent`、`policy_route`、`compact`、`transit_hint` | 组合Harness并增加阶段路由、ACT适配、用户意图门、紧凑上下文和回执提示 |
| 28 | `harness.settled_hold.install_isolated` | 最外层规划工厂增加显式请求的持握稳定等待；该安装器有重复调用哨兵 |

模型HTTP请求有三种独立变换：当前阶段筛选（`StageRequests`）、工具结果压缩（`CompactRequests`）、provider协议检查（`CheckedRequests`）。首次模型调用时，它们沿Harness调用路径按`StageRequests → CompactRequests → CheckedRequests → urllib`组合；响应和动作反馈不会被视为同一层证据。

## 已知边界与P1.3处理顺序

- 多个安装器修改模块级类、函数或工具列表，调用顺序会影响后续安装器读取到的基类和schema；新服务进程会重新从固定入口组合，现有运行不支持原地卸载/重新安装。
- `build_backend()`现在在同一进程只允许调用一次；再次调用会明确要求使用新进程。每层安装错误会带层名，阻止静默地在部分修改过的进程里继续重试。
- `/api/status`和`/health`的内部`runtime_composition`字段报告本进程实际Harness/Service MRO、安装顺序、planner factory和当前HTTP request中间件栈。当前空闲时只显示`CheckedRequests`；Stage/Compact包装在Harness的chat路径懒安装，需API请求后才会出现在活栈里。本轮没有为检查它们而调用真实API。
- 请求中间件使用共享的`harness.agent.urllib`模块别名，并在每个Harness的`chat()`路径懒安装。下一步再逐层迁移到实例级请求transport：先让一份fixture证明工具选择、上下文变换、provider检查及API失败不执行动作的行为完全一致，再删掉对应的全局包装。
- TAMP工厂会多次包装`sim.service.TampPlanner`。现在TAMP录制器会在具体planner实例构造后写一条`planner_runtime`事件，记录请求工厂、实际实例类、后端、任务和声明合同；其模块身份仍由运行manifest里的源码哈希约束。该新事件的完整归档路径尚未用一次独立TAMP服务运行端到端复核。
- `object_gpu`、`object_memory`、`waypoint_*`等未在日常入口被加载的研究/候选安装器，不计为活动能力；其名字相似不表示已部署。

首轮子项已完成：组合清单、单进程一次安装护栏、失败层名、运行时MRO/中间件报告和TAMP工厂/实例来源字段。下一小项：把请求transport作为单独层迁移，保持阶段包、上下文压缩和provider检查顺序以及失败语义。
